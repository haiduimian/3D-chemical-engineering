# 01 迭代流程（每轮从启到止）

> 配套：00-README（总纪律）｜02（验收命令）｜03（审查清单）｜04（模板）｜05（部署）

## 阶段 P0：上下文与定标（15 min）

1. 读最新 `docs/research/白皮书-项目现状与下一阶段开发.md`：
   - §1 当前架构（改动必须与其自洽）
   - §2 已废弃方案（**禁止**重复实现任何 ❌ 项）
   - §4 下一轮目标（Nx 队列，含量化指标）
   - §5 验收栈（本轮必跑清单）
2. 读上一轮 `迭代报告-roundN.md`（教训清单是"已知坑"，避免重蹈）。
3. 汇合用户指令：**用户显式指令 > 白皮书队列**。把本轮目标写成任务清单（todo），
   每条注明验收口径（数值）。若用户指令未在白皮书，把它加进本轮并回写白皮书。
4. 检查仓库卫生：`git status --short` + 清理僵尸 Edge（05 文档 §4）+ 确认 dev/preview 端口归属：
   - `Get-NetTCPConnection -LocalPort 5180,4173 -State Listen` → 5180 应被 vite dev 占用、
     4173 应被 vite preview 占用（vite 会拿第一个空闲端口，4037 只能由 `--strictPort` 保证）。

## 阶段 P1：调研（可选，30~90 min，需要外部依据时做）

- **大厂视觉/技术调研**：`node scripts/firecrawl-visual.mjs --out docs/research/firecrawl-visual-raw2.json`
  （keyless 被 IP 风控时冷却 90s 重试一次）；蒸馏为 `docs/research/参考基准-<主题>.md`。
- **库文档**：用 Context7（HTTP API 或工具）查 three.js 官方范式（如 R9 的
  `shadow.autoUpdate=false + needsUpdate` 静态场景范式）。
- **子代理调研**：可委派 web_search 子代理输出"对项目源码注释的调参建议"文件。
- 退出条件：已有可落地、可量化的调参/实现依据（数值或官方文档链接）。调研结论写入报告"调研结论"节。

## 阶段 P2：实现（2~4 h）

1. 按任务清单逐项改源码（文件纪律见 03 清单）。
2. **新数据结构必须同步"工程防线"**（同步修改/新增规则）：
   - 新增动态发光体 → `emissionInvariants.ts` 规则表；
   - 改端口口径/管线直径 → 口径审计自动覆盖（`auditPipePortSizes`），白名单需注明工艺语义；
   - 改设备/围堰/管廊布置 → 同步 `buildPatrolColliders()`；
   - 新增可调视觉参数 → 优先进 `timeOfDay.ts` 预设（统一插值/升降级）。
3. `npm run build` 必须通过（TS/打包零错误）才进入验收。
4. 实现在全部完成前**不要**跑任何 headless 探针（HMR 污染）。

## 阶段 P3：验收（1~2 h，全绿才算过）

顺序固定：
1. `npm run build`（重新构建 dist）
2. `npm run preview -- --port 4173 --strictPort`（如未运行；**每次 build 后确认 preview 服务的是新哈希**，
   必要时重启 preview 任务）
3. 快速探针（有亮度调整时必跑）：`node scripts/sky-preset-probe.mjs --url http://localhost:4173/3D-chemical-engineering/`
   （输出三档 fullMean/hiPct/skyRGB；均值互差 ≤±8% 且与上一轮基线漂移 <±5% 属正常）
4. `node scripts/patrol-collide-check.mjs`（若动过布置/碰撞表）
5. 全量认证：`node scripts/timeod-check.mjs --url ...4173... --out .shots/timeod-r<N>`（≈25~35 min）
6. `node scripts/capture-frames.mjs --url ...4173... --out .shots/frames-r<N> --frames 10 --interval 400 --clean --fast`
7. `node scripts/pipe-collision.mjs`（几何回归，**0 新增重叠**）
8. `node scripts/sky-initial-probe.mjs`（若动过 sky/烘焙，35s 时间线天空不黑化）

判定与失败处理：见 02 文档（每工具一节：预期输出/通过判据/失败排查）。**失败不跳过**——定位根因
（探针二分："执行到哪一行"）、修复、重跑。像素级问题用 `node scripts/sky-diagnose.mjs xxx.png` 做区域亮度定位。

## 阶段 P4：报告与方案（30~60 min）

1. 写 `docs/research/迭代报告-round<N>.md`（模板见 04）：问题定位表（根因+机制+证据）、
   修复/实现表、验收结果表（全部实测数值）、**过程踩坑教训**（至少 3 条，反哺 03 清单）、下轮方案摘要。
2. 升版 `白皮书-项目现状与下一阶段开发.md`：版本号 R<N>、§1 架构同步、§2 追加新 ❌ 条目、
   §3 痛点刷新、§4 下一轮 N<N+1> 量化目标、§5 验收栈（含新增工具）。
3. 新发现的可复用脚本（*.mjs 专项验证）连同用法写进白皮书工具链清单。

## 阶段 P5：交付（15 min，见 05 文档）

1. `git add -A` 前先审查 staged 清单（**只含本轮确认文件**；生成物/未知文件剔除，见 00-README §4）。
2. commit（信息规范：`feat(3d): R<N> <一句话>`）→ push main（token 注入 URL）。
3. 部署：worktree 方式更新 gh-pages 分支（05 §2），清除旧哈希资源。
4. 线上验证：`https://haiduimian.github.io/3D-chemical-engineering/` → HTTP 200 且引用新 JS 哈希。

## 退出条件（本轮完成判据）

- [ ] 任务清单全 completed
- [ ] build 通过
- [ ] 验收栈全绿（timeod ALL PASS / invariants PASS / sizeAudit 空 / 碰撞专项 PASS / 0 新增重叠）
- [ ] 迭代报告 + 白皮书已升版落盘
- [ ] main 与 gh-pages 已推送，线上 200 + 新哈希
- [ ] 回复用户：交付摘要 + 验收数值 + 教训 + 下轮方针（N 队列）
